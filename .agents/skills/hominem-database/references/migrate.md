# Goose migration workflow

Use this workflow for every schema change under `packages/db/migrations/`.

1. Create a flat SQL migration through the repository wrapper:

   ```bash
   just db create <domain_change>
   ```

   Goose generates the `YYYYMMDDHHMMSS_<domain>_<change>.sql` timestamped file. Do not use a live database URL for file creation.
2. Keep one concern per file. Split schema creation, backfills, indexes, policies, and triggers when they are separate concerns.
3. Include matching Goose `Up` and `Down` sections. Wrap multi-statement blocks in `-- +goose StatementBegin` and `-- +goose StatementEnd`.
4. Put SQL in the migration file. Never edit `packages/db/src/types/database.ts` by hand; it is generated by `kysely-codegen`.
5. Apply local migrations and regenerate types with an explicit database URL:

   ```bash
   export DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:5434/hominem"
   just db migrate
   just db codegen
   ```

6. Apply migrations to the test database:

   ```bash
   just db migrate test
   ```

7. Validate migration files with `goose validate` (included in `just db validate`), then apply and verify state with `just db validate test` or an explicitly selected database. `just db validate` is not read-only.
8. Exercise `Down` against a test database with `just db rollback test`. Non-test rollback requires explicit `ALLOW_DB_ROLLBACK=1`.
9. Run `just db lint` for filename/section checks and schema-qualified drop checks.
10. Review the migration and generated Kysely type diff. Run affected package tests and typechecks.

## Failure handling

- If Docker or Postgres is unavailable, do not start it automatically; report the prerequisite and stop at the blocked validation step.
- If `DATABASE_URL` is missing, set it explicitly for the intended database. There is no fallback.
- If migration syntax or markers fail, inspect `just db status`, correct the migration, and re-run validation.
- Do not use `goose reset`, `down-to 0`, or `--allow-missing` during normal development. These are recovery operations requiring explicit approval and a backup plan.

The repository uses chronological flat Goose migrations with descriptive suffixes, for example `20260709234400_create_app_calendar_import_tables.sql`.
